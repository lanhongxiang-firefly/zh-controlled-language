## 0 本轮范围

本轮只修订架构提案与接口设计：区分第一版必要能力、未来扩展能力与待决问题，消除接口矛盾，精简模板。

不执行：V0.2 内容迁移、现有技能文件修改、安装脚本修改、四个宿主安装副本修改、跨学科模拟测试。第 4 节的迁移方案是待批准的计划，不是已发生的改动。

## 1 设计点分级

## 2 现状审查（沿用 R1 结论）

现有技能包 9 个文件，三个耦合点：

1. `SKILL.md` 同时承担执行层与 Core 规则正文，新增学科必须改入口文件。
2. frontmatter `name`／`description` 绑定工程热物理，通用触发无法覆盖其他学科。
3. 单个 `tests/cases.json` 混合 Core 与学科用例，学科无法独立测试。

内容归属：`expression-issues.md` 基本为通用规则；`terminology-register.md` 以学科术语为主，其中法定计量单位与确凿错字属通用规范；`examples.md` 与测试用例混合 Core／Domain，25 条中约 5 条检验学科术语规则，其余为通用规则在学科语境下的示例。迁移时保留原文，按检验对象拆分归属。

## 3 第一版架构

### 3.1 四层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Core | 通用中文技术表达规则、术语治理机制、Error／Warning／Suggestion 分级、误判控制、原文保护 | 学科专属术语清单、文体模板 |
| Domain Pack | 专业术语与中英对应、译法依据、学科特有语言规范、本学科测试集 | 通用语言规则、其他学科内容、文体结构 |
| Writing Profile | 按文体调整适用强度与表达偏好 | 术语、译法、学科约束、Error 级规则 |
| Skill 执行层 | 读取 Core 与已加载模块、路由、冲突处置、按需审查记录 | 规则内容本身 |

四层职责划分保持不变；第一版不为其增加子层或治理层。

按 D-2，Core 只含通用语言规则与术语治理机制（含依据类别枚举、法定计量单位与通用字形规范），不持有科研专业词汇表。「误差」「测量不确定度」「显著」等跨学科词汇由各 Pack 按本领域定义与实际需要自行登记，不要求收录全部科研词汇。多 Pack 出现大量定义一致的重复词汇时再评估共享资源（F-7，Deferred）。

### 3.2 加载契约（Required v1）

- Core 始终加载，其 Error 级始终生效。
- 默认学科由使用者首次配置时写入 `skill/defaults.yaml`；单次任务默认使用该 Pack，不需重复声明。
- 用户明确要求时可临时切换到其他学科；切换只影响本次任务。
- 公开分发版本的 `defaults.yaml` 不带默认值，由使用者自行设置，不预设所有用户属于工程热物理。
- 本机（当前维护者环境）的默认学科为工程热物理；该默认值只写入本机配置，不进入公开版本。
- 配置缺失且用户未指定时，只加载 Core，不推断专业术语规范。
- 允许同时加载多个 Pack 与多个 Profile；两者为正交维度。
- Skill 构建本次会话的模块白名单，判定只引用白名单内的条目。
- 判定优先级：Core Error ＞ 已加载且状态为 Accepted 的 Pack 条目 ＞ Profile 的 Suggestion ＞ 未加载内容。
- 术语冲突：保留各词形与上下文，登记待确认，不强制统一。
- 状态为 Proposed／Disputed、依据类别空缺或依据不足：保留原词、标记待确认，不创造译法。

### 3.3 目录结构（第一版）

```text
project/
├── core/
│   ├── language-rules.md          # 通用规则、分级、误判控制
│   ├── terminology-governance.md  # 三层机制与条目格式
│   └── quality-control.md         # 保留项、测试规范
├── domains/
│   └── engineering-thermophysics/ # 首个 Pack，迁移时建立
│       ├── manifest.yaml
│       ├── terminology.md
│       ├── rules.md
│       └── tests/cases.json
├── profiles/
│   └── technical-documentation/   # 第一版 1 个示例 Profile
│       └── profile.md
├── skill/
│   ├── SKILL.md                   # 仅执行层；技能包按 D-1 更名，旧名保留别名
│   └── defaults.yaml              # default_domain；公开版为空，本机填工程热物理
├── tests/
│   ├── run_tests.py               # 通用执行器，接受模块目录参数
│   └── integration.json           # 组合与误用检测用例
├── docs/architecture/             # ADR、接口、贡献指南、模板
├── experiment/                    # 保留：V0.1 历史实验
├── install_skills.py              # 迁移后按 manifest 组装
└── dist/                          # 打包产物
```

相对 R1 的收敛：`core/` 由三个子目录改为三个文件；`profiles/` 由 6 个目录改为 1 个示例；`tests/` 由三层目录改为 1 个执行器加 1 个集成用例文件；移除根 README／LICENSE 与模块级版本矩阵。保留 `experiment/`、安装脚本与产物目录，避免破坏证据链与四宿主安装。

### 3.4 状态词约定

模块级只有 `enabled: true/false`；条目级使用 `Proposed／Accepted／Deprecated／Disputed`。两套状态互不混用。R1 中模块级 `draft/active/deprecated` 已移除。

### 4.2 功能不丢失核对表

| V0.2 能力 | 迁移后承载 | 回归检查 |
| --- | --- | --- |
| 四类场景、七类文本按强度适用 | Profile 与加载表 | 集成用例覆盖 7 类文本 |

| 25 条测试与误判记录 | 三处用例集 | 总数不减、误判基线持平 |

### 4.3 实施阶段

1. 建立 `core/` 三个文件，不删旧文件。
2. 建立 `domains/engineering-thermophysics/`，复制并重组内容。
3. 按 D-1 更名技能包，改写 `skill/SKILL.md` 为纯执行层并接入白名单路由，保留旧名别名映射。
4. 拆分用例，泛化执行器，跑 Core／Pack／集成三组测试；用最小 stub Pack 验证「不改 Core 与 Skill 即可扩展」。
5. 建立 `skill/defaults.yaml`（公开版空、本机填工程热物理），改造 `install_skills.py` 与四宿主副本并复验。

回滚：任一阶段失败时，由源目录 9 个文件重建四宿主副本；阶段 1–3 全程保留旧文件。

## 7 修订说明（R1 → R2）

## 8 维护者决策（已决定，2026-11-11）

以下三项已由维护者决定。原方案比较保留为决策依据，不再作为待选项。

| 编号 | 结论 | 方案比较要点 | 落实位置 |
| --- | --- | --- | --- |
| D-1 | **A**：技能更名为通用名，旧名保留别名 | A 需同步四宿主目录、description、安装脚本与产物；B 会形成两套并存 | 3.3、4.1、4.3 阶段 3 |
| D-2 | **B**：跨学科科研词汇由各 Pack 自行登记，Core 不承担科研专业词汇表 | A 减少重复但需界定 Core 边界；B 边界清晰、各 Pack 按本领域定义登记 | 3.1 边界说明、4.1 术语表映射 |
| D-3 | **维护者提出的默认学科方案**（比原 A／B 更简单） | 原 A 仅显式指定、原 B 依赖覆盖文件；新方案以一次配置的默认值取代每次声明 | 3.2 加载契约、`skill/defaults.yaml`、4.3 阶段 5 |

**D-2 维护者理由**：

1. Core 应只管理通用语言规则和术语治理机制，不承担科研专业词汇表。
2. 「误差」「测量不确定度」「显著」等词虽跨学科使用，但具体定义和使用语境可能不同。
3. 各 Pack 只登记本领域实际需要规范的词汇，不要求收录所有科研词汇。
4. 若未来多个学科确实存在大量定义一致、重复维护的词汇，再考虑抽取共享资源（记为 F-7，Deferred）。

**D-3 方案要点**：

- 个人默认学科：使用者首次配置时指定；本机默认值为工程热物理。
- 单次任务：默认使用该 Pack，不需重复声明。
- 临时切换：用户明确要求时切换到其他学科，只影响本次任务。
- 公开版本：不预设所有用户属于工程热物理，由使用者自行设置默认学科；`defaults.yaml` 不带默认值。
- 配置缺失且用户未指定时，只加载 Core。

**Deferred（记录，不需现在决定）**：F-1 Profile 粒度是否扩展为 6 类；F-2 依据类别枚举与出处登记格式细化；F-3 语义化版本与兼容矩阵；F-5 领域复核角色与升级审批流程；F-7 共享科研词汇资源抽取（D-2 理由 4）；F-4 的多渠道发布部分。原 F-4 的许可证选型已由维护者于 2026-11-11 决定，见第 9 节；原 F-6「四宿主目录名是否随 D-1 调整」已由 D-1 = A 决定，不再列为待定项。
